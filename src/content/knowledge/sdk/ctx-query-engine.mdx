# How `ctx` Works

The `ctx` language is a thin command layer over the SDK graph runtime.

For most consumers, the recommended graph API is:

- `parseGraphDsl()`
- `queryGraph()`
- `buildContextPack()`

If you need help choosing between those methods and the lower-level graph primitives, see:

- [SDK Interface Reference](./sdk-interface-reference.mdx)
- [Graph API Guide](./sdk-graph-api-guide.mdx)

Internally, a `ctx` query is executed in four steps:

1. Resolve a root
2. Traverse the graph
3. Filter and rank results
4. Package a context bundle under budget

## 1. Root Resolution

`ctx` starts by turning the target into one or more root seeds.

Examples:

- text query: file, section, and entity search
- `@id`: direct graph node lookup
- `/path`: path or file reference resolution
- `#tag`: tag-based node selection
- `%type`: type-based node selection

The `in` clause is applied during seed resolution so irrelevant roots do not enter traversal.

## 2. Graph Traversal

After seeds are resolved, the graph runtime walks outward across allowed edges.

Traversal is controlled by:

- `via`: allowed relation names
- `depth`: maximum hop count
- `limit`: node cap

The public relation names map to internal graph edge types:

- `related -> RELATES_TO`
- `depends_on -> DEPENDS_ON`
- `implements -> IMPLEMENTS`
- `references -> REFERENCES`
- `parent -> PARENT_SECTION`
- `child -> CHILD_SECTION`
- `supersedes -> SUPERSEDES`

## 3. Filtering And Ranking

The engine then narrows and ranks the candidate neighborhood.

Filtering sources:

- `in`: content path prefix restriction
- `where`: metadata filtering
- built-in node/model constraints from the typed query request

Ranking sources:

- graph distance
- edge weights
- canonicality
- stage-aware boosts from `for`
- basic recency and metadata hints already present on graph nodes

Stage-aware ranking is intentionally heuristic in v1. It biases the same graph differently depending on whether the caller wants planning, implementation, research, debugging, or review context.

## 4. Context Packaging

Finally, the engine shapes the output according to `as` and `budget`.

Views:

- `list`: minimal node inventory
- `brief`: compressed excerpts
- `full`: larger excerpts
- `map`: graph-oriented summary with edge reasons

The packer deduplicates nodes, estimates token usage, and stops once the requested budget is reached.

## SDK Mapping

The public `ctx` surface maps onto these SDK entrypoints:

- `parseGraphDsl()`
- `resolveSeeds()`
- `queryGraph()`
- `buildContextPack()`

These are the preferred graph/context methods. Lower-level lexical and topology methods still exist, but they are considered advanced primitives.

Typical flow:

```ts
import { AgentSdk } from '@treeseed/sdk';

const sdk = new AgentSdk();

const parsed = await sdk.parseGraphDsl(
  'ctx "queue api" for implement in /knowledge via implements,references depth 1 budget 4000 as full',
);

if (!parsed.ok || !parsed.query) {
  throw new Error(parsed.errors.join('; '));
}

const graph = await sdk.queryGraph(parsed.query);
const pack = await sdk.buildContextPack(parsed.query);
```

## Design Constraints In V1

Deliberate non-features:

- no nested boolean filter expressions
- no explicit scoring syntax
- no custom traversal algorithms in the language
- no compatibility support for the old `key=value` DSL

That keeps the command easy for both humans and agents while preserving room to evolve the engine later.
