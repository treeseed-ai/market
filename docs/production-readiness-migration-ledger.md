# Production Readiness Migration Ledger

This document is the durable execution ledger for the Platform, Market gateway, repository, and content-authority migration. Update it whenever a migration checkpoint changes live state, exposes a blocker, or closes a production-readiness gate. Architectural intent remains in `docs/project-architecture-migration.md` and `docs/package-ownership.md`; this ledger records execution status and evidence.

## Destination

The completed system has two operational domains:

- `treeseed-ai/platform` is the public Apache-2.0 installer and manager for customer deployments. It composes independent Admin, API, Agent, AI, CLI, Core, Reviewer, SDK, TreeDX, UI, fixture, and template repositories. It cannot check out or provision Market or Market API.
- `api.treeseed.dev` is the singleton gateway. Private Market API owns `/v1/market/**`; all declared hosted Admin routes pass through to a separately deployed public AGPL-3.0 Admin API service.
- Default deployments use the singleton URL for both control-plane and Market traffic. Sovereign deployments use a customer control plane for tenant data and the singleton gateway only for registry, commerce, licensing, and ecosystem governance.
- Every product project has an independently governed content repository. Git is durable history, TreeDX is the operational content plane, and immutable R2 releases are the runtime plane. Content repositories are never Platform workset checkouts.
- All development for all 31 repositories runs through a TreeSeed instance. Admin UI, CLI, interactive Codex, and autonomous agents use one API-owned proposal, decision, workday, capacity, assignment, checkpoint, receipt, stage, and release lifecycle. Local instances are supported control planes; unrestricted local source editing is not a supported development strategy.

The last item is the critical completion outcome. Repository migration, content separation, and provider reconciliation are enabling work, but the migration is not complete until the system can plan and implement a real multi-project initiative through agents and then fails closed when the same source changes are attempted outside an admitted assignment.

Codex is the default agent execution provider, with explicit policy-based overrides allowed. API is the sole durable action owner; CLI must expose every API action, UI must consume those same contracts, and agent tools must be assignment-scoped projections of them. Complete API/CLI parity plus a CLI-driven dogfood initiative are therefore completion evidence, not optional operator convenience.

## Resource Creation, Team Inventory, Workset, and Receipt Roles

The live team project inventory is the logical successor to the old parent-repository submodule map. A seed is only a resource-creation input:

1. A seed creates or adopts initial team resources; it does not remain current membership authority.
2. The live team project inventory resolves the Platform-managed software subset and repository bindings; exact Git commits are observed when a workset is materialized and frozen only in receipts.
3. `trsd platform workset` observes live branch heads and materializes exact commits as independent assignment-owned repositories. The directory layout is disposable custody, not developer authority.
4. `trsd save` creates a repository-scoped checkpoint by default.
5. `trsd save --federated` records exact pushed commits, dependency edges, contract digests, and remote proof in a `treeseed.integration-change-set/v1` receipt.
6. Stage and release consume verified receipts. Gitlinks are not promotion authority.

Governed agent execution now adds an authority layer before save: a reviewed assignment checkpoint produces a stable workset-local execution-authority receipt, and save embeds it only when repository identity, branch, and commit ancestry still match. This connects proposal/decision authority to exact source evidence without making local layout authoritative.

Cross-project coordination does not widen proposal authority. Every source-changing project in the unified Codex/CLI development path must have its own project-local proposal, accepted decision, planning and capacity-plan provenance, assignment graph, reviewed checkpoint, and receipt. Dependencies only link those independent authority chains and make downstream promotion fail when an upstream decision is missing, stale, or superseded. An umbrella objective may organize the initiative but cannot create assignments outside its project.

The final Codex/CLI path has one lifecycle: proposal, accepted decision, planning workday, estimate, accepted capacity plan, acting workday, project-scoped assignment, review, and receipt. The team project inventory supplies repository discovery and local materialization; it does not replace capacity admission. Direct ungoverned edits remain transitional legacy behavior and must not be considered staging-eligible after the unified gate is enabled.

Affected repositories are deliberately not frozen when a proposal begins. Planning workdays use the live team project inventory to discover dependencies and produce estimates. Accepted capacity plans and assignments freeze agent acting scope; an acting agent that discovers another repository must record the dependency and return it to planning rather than widen its assignment. Planning may expand read-only inventory inspection, but writable repository custody remains assignment-scoped. Exact repository promotion scope becomes immutable in the saved integration receipt and staging candidate.

The obsolete `treeseed.portfolio.json` authority path has been removed from SDK workset planning, managed-repository discovery, lifecycle fixtures, and generated Platform snapshots. The API now exposes an authorized team project inventory, and CLI workset planning converts that inventory into live-ref observations. Live local verification resolves exactly 13 Platform workset repositories: 12 managed primary repositories plus the unpaired fixture repository. Market, Market API, content repositories, and archived legacy template identities are absent.

The remaining transition is to stop using the Market workspace's compatibility gitlinks after active development moves to Platform worksets and the Platform snapshot can be promoted from reviewed federation evidence.

The architecture is not fully cut over because the old Market checkout still provides compatibility materialization and Platform-root authority is not yet represented in the child workset receipt.
