# TreeSeed Operational App UI Specification

This document replaces the legacy app specification. The authenticated app is no longer organized around retired section routes or a resource-discovery-first workflow. The current product surface is operational infrastructure for coordinating workdays, governance, knowledge, and advanced runtime context.

## Product Frame

TreeSeed should feel like calm industrial operations tooling:

```text
Objective
  -> Workday
  -> Execution
  -> Governance
  -> Knowledge
```

The UI should communicate that automation-supported work is structured, repository-grounded, reviewed, and retained as organizational memory.

## Primary App IA

The authenticated app has five primary sections:

```text
/app                 Mission Control
/app/workdays        Workdays
/app/governance      Governance
/app/knowledge       Knowledge
/app/infrastructure  Infrastructure
```

Additional app routes should be contextual detail surfaces under these sections, such as workday detail, approval review, knowledge entry detail, and Infrastructure subroutes.

## Mission Control

Mission Control is the organization’s operational overview.

It should show:

* current objective
* active workdays
* queued operational work
* pending approvals
* repository health
* recent knowledge produced
* recent decisions and releases
* operational metrics

Mission Control should answer what is happening, what needs attention, and what durable memory has been produced.

## Workdays

Workdays are the core product abstraction.

A workday detail surface should be organized around:

* objective and state header
* phase strip
* grouped operational timeline
* artifacts
* repository context
* governance
* knowledge outputs

The dominant language should be Research, Implementation, Verification, Governance, and Knowledge. Raw prompts, task payload internals, agent IDs, runner tokens, and simulated chatter should not appear in the primary UX.

## Governance

Governance is a first-class review system.

It should show:

* pending approvals
* escalations
* review timeline
* audit trail
* policies
* capacity and budget constraints

Approval detail pages should provide context, policy snapshots, related workdays, related repositories, operational artifacts, audit events, and deliberate decision actions.

## Knowledge

Knowledge is institutional operational memory.

The Knowledge index should unify:

* Architecture
* Operations
* Research
* Implementation
* Decisions
* Reports
* Releases
* Imports

Every knowledge entry should show operational metadata where available: produced during, generated by, approved by, repositories referenced, related workdays, related approvals, related deployments, related reports, and related decisions.

## Infrastructure

Infrastructure is advanced operator tooling.

It should contain:

* system overview
* teams and projects as operational context
* repositories
* deployments
* capacity and budget
* workers and queues
* hosts and integrations
* resources and imports
* seeds
* policies and diagnostics

Infrastructure may be dense and technical, but it should only expose presentation-safe operational labels and states.

## Resource Language

Public resource and backend catalog systems may keep exact technical names where they are real contracts. Authenticated app UX should frame these concepts as:

* operational resources
* imports
* reusable workflows
* knowledge imports
* execution extensions
* published operational assets

Resources belong contextually under Knowledge and Infrastructure, not as the primary app onboarding model.

## Visual Requirements

The app-wide design language should be:

* dense and inspectable
* high-contrast
* calm
* status-aware
* accessible by keyboard
* restrained in motion
* semantically colored for risk, severity, governance, and system state

Cards, panels, tables, timelines, queues, phase strips, and infrastructure grids should maintain stable dimensions and avoid decorative visual noise.

## Non-Goals

Do not reintroduce:

* retired section-first app navigation
* compatibility redirects to retired app section routes
* resource-discovery-first onboarding
* prompt-centric workflows
* agent spectacle
* raw task payload displays
* runner-token or secret exposure
* demo-only app functionality

## Completion Status

The UI migration is complete through Phase 7. Future UI work should extend the operational IA above and should keep teams, projects, resources, and runtime details as contextual infrastructure rather than primary product framing.
